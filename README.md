# RiveSkia.Avalonia

Rive-рантайм для Avalonia, рисующий через SkiaSharp.

Библиотека построена на актуальном C++-ядре Rive ([rive-runtime](https://github.com/rive-app/rive-runtime)) — в отличие от заброшенного [rive-sharp](https://github.com/rive-app/rive-sharp), который пришпилен к версии ядра начала 2025 года и не открывает файлы из современного редактора.

Ядро Rive загружает `.riv`, крутит стейт-машины и считает геометрию кадра, но само ничего не рисует — оно диктует команды абстрактному рендереру. Эта библиотека реализует такой рендерер поверх `SKCanvas`, а Avalonia уже показывает результат.

## Требования

| | |
|---|---|
| ОС | Windows x64 |

## Установка

Пакет не опубликован на nuget.org, поэтому подключается из локальной папки.

1. Положи `RiveSkia.Avalonia.0.2.2.nupkg` в любую папку, например `C:\nuget-local\`.

2. В своём проекте:

```powershell
dotnet add package RiveSkia.Avalonia --source C:\nuget-local
```

Чтобы не указывать `--source` каждый раз, зарегистрируй папку как постоянный источник:

```powershell
dotnet nuget add source C:\nuget-local --name RiveSkiaLocal
```

Нативная `rive_shim.dll` приезжает вместе с пакетом (`runtimes/win-x64/native/`) и копируется в выходную папку автоматически — руками ничего перекладывать не нужно.

## Быстрый старт

Создание проекта с нуля:

```powershell
dotnet new install Avalonia.Templates
dotnet new avalonia.app -n MyApp
cd MyApp
dotnet add package RiveSkia.Avalonia --source C:\nuget-local
```

Положи `.riv` в папку `Assets` и пропиши копирование в `MyApp.csproj`:

```xml
<ItemGroup>
  <None Include="Assets\teddy.riv" CopyToOutputDirectory="PreserveNewest" />
</ItemGroup>
```

`MainWindow.axaml.cs`:

```csharp
using System;
using System.IO;
using Avalonia.Controls;
using RiveSkia;

public partial class MainWindow : Window
{
    public MainWindow()
    {
        InitializeComponent();

        var path = Path.Combine(AppContext.BaseDirectory, "Assets", "teddy.riv");
        Content = new RiveControl(path);
    }
}
```

Запуск:

```powershell
dotnet run
```

## API

### `RiveControl`

```csharp
public class RiveControl : Control, IDisposable
{
    public RiveControl(string rivPath);
    public RiveControl(RiveFile file);

    public void SetInputBool(string name, bool value);
    public bool GetInputBool(string name);
    public void SetInputNumber(string name, float value);
    public float GetInputNumber(string name);
    public void FireInputTrigger(string name);
    public IReadOnlyList<RiveInput> GetInputs();

    public void Dispose();
}

public enum RiveInputKind { Bool, Number, Trigger }
public readonly record struct RiveInput(string Name, RiveInputKind Kind);
```

Контрол загружает файл, берёт нулевой артборд, запускает его стейт-машину по умолчанию (при её отсутствии — первую по индексу) и анимирует по таймеру. Содержимое вписывается в границы контрола по правилу `contain` с центрированием.

Путь в `RiveControl(string rivPath)` — **физический файл на диске**. Схема `avares://` пока не поддерживается.

Указатель мыши (наведение, нажатие, отпускание, уход курсора) автоматически прокидывается в стейт-машину — если файл содержит слушатели ("listeners") на эти события, они сработают сами, без дополнительного кода. Координаты корректно пересчитываются из пикселей контрола в локальную систему артборда с учётом вписывания `contain`.

Входы стейт-машины (`Boolean`/`Number`/`Trigger`, заданные в редакторе Rive на вкладке State Machine) управляются по имени через `SetInputBool`/`SetInputNumber`/`FireInputTrigger`. Обращение к несуществующему имени — не исключение, а тихий no-op. Сами имена не нужно подбирать вслепую или смотреть в редакторе — `GetInputs()` возвращает список того, что реально есть в загруженном файле:
```csharp
foreach (var input in control.GetInputs())
    Console.WriteLine($"{input.Name}: {input.Kind}");
```

`RiveControl` реализует `IDisposable` и освобождает нативные ресурсы автоматически при удалении из визуального дерева — вызывать `Dispose()` вручную обычно не нужно. После `Dispose()` контрол повторно не оживает, даже если его вернуть в дерево.

### `RiveFile`

```csharp
public sealed class RiveFile : IDisposable
{
    public RiveFile(string rivPath);
    public void Dispose();
}
```

Распарсенный `.riv`-файл, который можно переиспользовать в нескольких `RiveControl` — полезно, когда одна и та же анимация показывается много раз (например, иконка в списке): файл читается и парсится один раз, а не при создании каждого контрола.

```csharp
var file = new RiveFile(path);
var a = new RiveControl(file);
var b = new RiveControl(file); // тот же распарсенный файл, свой независимый инстанс артборда/машины
```

`RiveControl`, созданный так, **не владеет** файлом и не разрушает его при своём `Dispose()` — жизненный цикл `RiveFile` нужно вести отдельно (например, диспозить, когда закрываются все использующие его контролы).

## Что поддерживается

- Векторные фигуры: заливки, обводки, толщина, соединения и окончания линий
- Линейные и радиальные градиенты
- Клипы
- Прозрачность, в том числе вложенная
- Feather / мягкое размытие краёв
- Стейт-машины и анимации
- Layouts, data binding и текст на уровне ядра
- Интерактив: указатель мыши (hover/down/up/exit) и управление входами стейт-машины из кода
- Перечисление имён и типов входов стейт-машины (`GetInputs()`) — не нужно подбирать вслепую
- Переиспользование одного распарсенного файла в нескольких контролах (`RiveFile`)

## Что пока нет

| Возможность | Поведение сейчас |
|---|---|
| Растровые изображения | не отрисовываются |
| Меши и кости | не отрисовываются |
| Режимы наложения | всё рисуется как `SrcOver` |
| Выбор артборда и стейт-машины | всегда нулевой / по умолчанию |

Проверить конкретный файл до интеграции удобно эталонным плеером из rive-runtime — он работает на том же ядре:

```powershell
player.exe -b d3d путь\к\файлу.riv
```

Если у плеера красиво, а в библиотеке нет — значит дело в одном из пунктов выше.

## Сборка из исходников

### Структура

```
RiveSkia/
├── native/                     нативная шимка (C++)
│   ├── rive_shim.cpp
│   └── build.ps1
├── src/
│   └── RiveSkia.Avalonia/      библиотека (C#)
└── cs/RiveDemo/                демо-приложение
```

### 1. Ядро Rive

Нужны Visual Studio 2022+ с компонентами *C++ Clang Compiler for Windows* и *MSBuild support for LLVM (clang-cl)*, Git for Windows с unix-утилитами в PATH, GNU make и Python 3.

```powershell
git clone https://github.com/rive-app/rive-runtime.git
cd rive-runtime\tests
..\build\build_rive.ps1 release
```

На выходе в `tests\out\release\`: `rive.lib`, `rive_harfbuzz.lib`, `rive_sheenbidi.lib`, `rive_yoga.lib`, `rive_decoders.lib` и сопутствующие.

### 2. Шимка

Сборка обязательно в **x64**-окружении Developer PowerShell — `build.ps1` проверяет это сам и при необходимости инициализирует.

```powershell
cd native
.\build.ps1
```

Критично: флаги и дефайны шимки (`/MT`, `/GR-`, `_HAS_EXCEPTIONS=0`, `WITH_RIVE_TEXT`, `WITH_RIVE_LAYOUT`, `RIVE_ORE` и остальные) должны совпадать с теми, которыми собрано ядро. Расхождение хотя бы в одном меняет раскладку классов в заголовках и даёт порчу памяти вместо ошибки компиляции.

### 3. Пакет

```powershell
cd src\RiveSkia.Avalonia
dotnet pack -c Release
```

После любого изменения C++ сначала пересобирай шимку, потом пакет — иначе внутрь уедет старая нативная библиотека.

Проверка, что нативная часть упакована:

```powershell
Copy-Item bin\Release\RiveSkia.Avalonia.0.2.2.nupkg $env:TEMP\pkg.zip -Force
Expand-Archive $env:TEMP\pkg.zip -DestinationPath $env:TEMP\pkg -Force
dir $env:TEMP\pkg\runtimes\win-x64\native
```

## Архитектура

Три слоя:

**`librive.a` (C++)** — ядро Rive без изменений. Парсит `.riv`, продвигает стейт-машины, обходит дерево артборда и вызывает методы абстрактного `rive::Renderer`.

**`rive_shim.dll` (C++)** — реализация `rive::Renderer`, `rive::Factory`, `RenderPath`, `RenderPaint` и `RenderShader`. Ничего не рисует: каждый вызов транслируется в указатель на функцию, ведущий в C#. Геометрия накапливается в `RawPath` и отдаётся наружу целиком, а не по одной команде.

**`RiveSkia.Avalonia` (C#)** — принимает вызовы и переводит в `SKCanvas`. Пути кэшируются по (id, версия): геометрия перечитывается из натива только когда меняется, а не каждый кадр заново. Метаданные пути (число verb/point, fill rule, версия) забираются одним вызовом (`rive_path_info`), а не четырьмя по отдельности; буферы под сырые данные переиспользуются между кадрами и растут только когда путь стал больше, чем был.

Такое разделение выбрано намеренно: линковать Skia в C++ нельзя, поскольку в процессе уже загружена `libSkiaSharp`, и вторая копия Skia привела бы к конфликту символов.

Значения `PathVerb`, `FillRule`, `StrokeJoin` и `StrokeCap` в Rive совпадают со Skia, поэтому трансляция геометрии почти бесплатная. `Mat2D` раскладывается как `{xx, xy, yx, yy, tx, ty}` и переводится в `SKMatrix` перестановкой.

## Известные особенности

**Версия SkiaSharp.** Библиотека закреплена на той же версии, что тянет Avalonia (3.119.4). Две разные нативные `libSkiaSharp` в одном процессе приводят к падению, поэтому версию нельзя поднимать в отрыве от Avalonia.

**Артборд обрезает содержимое.** Если персонаж выходит за границы артборда, он будет срезан — это штатное поведение Rive, а не дефект отрисовки. Эталонный плеер ведёт себя так же.

**Кэш путей растёт, если ядро создаёт новую геометрию вместо переиспользования старой.** Геометрия кэшируется по (id, версия) и корректно перечитывается при изменении — заморозки на первом кадре нет. Но если для фигуры каждый раз заводится новый объект геометрии (не тот же id, перезаписанный через `rewind()`), запись в кэше остаётся навсегда: колбэка на удаление геометрии из натива пока нет.

**Шаг анимации привязан к реальному времени.** Внутри — fixed-timestep с аккумулятором: в ядро Rive всегда уходит стабильный шаг `1/60`, а таймер (4 мс, не ограничивает — упирается только в vsync монитора) лишь определяет, сколько таких шагов накопилось. Скачок долгого кадра не ускоряет и не дестабилизирует анимацию.

**Все экземпляры `RiveControl` синхронизированы одним общим локом.** Подтверждено эмпирически: `Advance` (UI-поток) и `Render` (поток компоновки Avalonia) — разные потоки, а шимка (`rive_shim.cpp`) хранит геометрию/краски/шейдеры **всех** сцен процесса в общих `std::unordered_map` и общем `g_cb` — без синхронизации несколько одновременно анимируемых контролов ловили реальный краш (access violation в `rive_artboard_draw_fit`). Лок в `RiveScene` статический (на весь процесс, не на экземпляр) по этой причине — оборачивает `Advance`/`Render`/`Dispose`/входы/указатель у **любого** контрола. Плюс есть защита от use-after-free: композитор Avalonia может поставить `Render` в очередь на UI-потоке и выполнить чуть позже на потоке композиции — если контрол успевает `Dispose()`-нуться в этот промежуток, `Render` для него молча ничего не делает вместо обращения к уже освобождённым `_artboard`/`_sm`.

**При большом числе одновременно анимируемых контролов (50+) FPS реально падает — и это не лок.** Замерено напрямую: при ~40 объектах на общий лок уходит **~15-20%** времени, остальное — сама работа (`rive_artboard_draw_fit`, маршалинг геометрии, построение `SKPath`/`SKPaint`). Убрать глобальность лока (сделать состояние шимки per-scene вместо process-wide) вернуло бы от силы ту же четверть — не тот масштаб, который решает проблему. Реальный потолок — суммарный объём геометрии, который нужно пересчитать и перерисовать каждый кадр; для сцен, где почти вся геометрия анимируется органически (не только трансформации), кэш путей тоже почти не помогает — версия меняется каждый кадр у большинства фигур.
